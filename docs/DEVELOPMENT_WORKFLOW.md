# AI 輔助開發流程（BabyApp 專案化版本）

> 原始模板是一份跨專案流程；這一份已經依 BabyApp 填好設定。通用流程的部分保持原樣，專案特有的事寫在「專案化設定」與各段落的「BabyApp 備註」裡。

## 專案化設定

| 設定 | BabyApp 的值 |
|---|---|
| 專案入口／主要指引 | `CLAUDE.md`（每次對話自動載入；架構、鐵律、選單、素材現況） |
| 專案技術與修改規則 | `CLAUDE.md` 的「鐵律」一節；細節在 `README.md` |
| 知識來源與搜尋順序 | `CLAUDE.md` → `README.md` 與 `docs/`（素材授權、語音素材指南、AI圖片生成指南）→ 程式碼本身（`Assets/BabyApp/Scripts`）與 `CardManifest.csv` → 外部資料／模型一般知識。沒有獨立知識庫。 |

| 實作或文件產出落點 | 程式：`Assets/BabyApp/Scripts/{Runtime,Editor}`；場景與預置物只由 `BabyAppSceneBuilder` 產生，不手動改；素材：`Assets/BabyApp/Art`、`Audio`；卡片內容：`Assets/BabyApp/CardManifest.csv`；工具腳本：`tools/`；文件：`docs/`。 |

| 需要人工處理的阻塞事項 | 直接在對話裡問使用者；下載檔案、刪除檔案、用使用者的帳號操作網站（Gemini 等）一律先問。 |
| Generator 重試上限 | 3 |

## 目標與適用範圍

以可追蹤、可驗證、可恢復的方式完成需求釐清、方案規劃、實作與驗收。適用於程式修改、技術文件、架構方案及素材整理；各類任務可省略不適用的階段，但不得省略必要驗證。

## 角色與責任

| 角色 | 責任 | 不應做的事 |
|---|---|---|
| Coordinator | 判斷任務範圍、安排流程、追蹤狀態、決定完成／重試／回退／升級 | 代替 Planner 做需求分析，或代替 Generator 產出主要交付物 |
| Planner | 釐清需求與限制、查閱現有程式和知識、提出方案與驗收條件 | 在需求或關鍵取捨不明時自行猜定；越權修改非其負責的產出 |
| Generator | 依已確認的方案實作程式或產出文件 | 擴大需求範圍、擅自改寫規格或無關重構 |
| Evaluator | 對照需求與驗收條件檢查產出，報告事實、差異及未驗證項 | 修改交付物，或自行決定重試／回退 |

**BabyApp 備註**：這是一個人的專案，絕大多數任務由同一個 Claude 對話依序扮演四個角色即可，不需要真的開子代理。只有「整批重做素材」「跨多個畫面的新功能」這種規模才值得拆成多個代理或多個對話。

## 標準流程

```text
使用者需求
  → Coordinator：分類、界定範圍、追蹤狀態
  → Planner：釐清需求、讀取既有資料、產出方案與驗收條件
  → Generator：按方案實作或產出
  → Evaluator：逐項驗證並回報
  → Coordinator：完成、重試、回退或升級
```

### 1. 需求與範圍

- 將需求整理成目標、範圍、限制、依賴與成功條件。
- 先讀 `CLAUDE.md`、相關程式／文件、直接呼叫方，再提出修改方案。
- 遇到多種合理解讀、重大設計取捨或無法驗證的前提時，先向使用者釐清，不要默默選擇。
- 拆分必要工作與非必要改善；非必要項目不併入本次變更。

**BabyApp 備註**：所有設計決定都要過「2～3 歲」這一關——沒有分數、計時、關卡、答錯懲罰；按鈕用圖示不用字；每個動作 100ms 內要有反應。這些是鐵律，不是可取捨的方案。

### 2. 規劃

Planner 的輸出至少包含：

- 需求摘要與明確假設。
- 預計修改的檔案、模組或文件。
- 實作步驟及相依關係。
- 每項需求對應的驗收條件。
- 風險、未決問題及需要人工確認的事項。

規格若需迭代，更新 `docs/specs/` 裡的正式落點，不另造互相矛盾的副本。

### 3. 實作或產出

- 僅依確認的規格與範圍工作；發現規格矛盾或缺漏時回報，必要時退回 Planner。
- 修改前理解既有 API、資料流、呼叫關係、序列化資料（`CardDeck` 資產、場景）及相關共用模組（`VoiceService`、`PromptLibrary`、`AppSettings`、`Strings`）。
- 採取最小且完整的修改；遵循專案既有命名、架構、格式與錯誤處理慣例（繁中註解、英文識別字、`[SerializeField] private` + Builder 接線）。
- 不加入未要求的功能、抽象層或投機性錯誤處理。
- 不覆蓋或清理與本次任務無關的既有變更。

**BabyApp 備註**：
- 改版面 → 改 `BabyAppSceneBuilder`，然後自己用 `execute_menu_item` 跑「3. 重建場景」；改 CSV 或素材 → 跑「2. 匯入卡片素材」；改 `BabyAppPlayerSetup` → 跑「4. 套用播放器設定」（否則只改了程式、`ProjectSettings` 沒吃到）。跑完一定要 `read_console` 確認沒有紅字。MCP 連不上時才改成請使用者跑，並在回報裡明說要跑哪一個。
- 新畫面要接進 `AppRoot`、`HomeScreen`（或 `DeckPickScreen`）、Builder 三處，少一處就是「有程式但進不去」。
- 新文字一律加進 `Strings`（中英各一），新台詞加進 `tools/prompts.csv` 並跑 `make-prompts.ps1`。

### 4. 驗收

Evaluator 逐項對照需求與驗收條件，檢查：

- 交付物是否符合需求，是否有遺漏或超出範圍。
- 編譯是否 0 錯誤（`read_console`；MCP 連不上才退回型別檢查）；若改了 Builder，接線欄位名是否與程式的 `[SerializeField]` 一致（`Wire` 找不到欄位會印紅字，`read_console` 看得到）。
- 邊界條件、相容性及受影響的呼叫方是否已驗證。
- 哪些項目未執行、無法執行或仍有不確定性。

**BabyApp 備註**：Claude 做得到的驗證是「編譯過」（`read_console` 0 錯誤）、「選單跑過」（`execute_menu_item` 的回傳）、「場景階層對」（`manage_scene`／`manage_gameobject`）與「檔案存在、尺寸正確、去背正確」；「畫面長這樣」「聲音聽起來對」永遠是 NOT_RUN，要列成給使用者的具體檢查步驟（在哪一頁、按什麼、應該看到／聽到什麼）。**「編譯過」要附 `read_console` 的實際輸出當證據；拿不到證據就寫 NOT_RUN，不得憑「應該會過」寫成 PASS。**

### 5. 流程決策與錯誤恢復

| 驗收結果／錯誤類型 | Coordinator 動作 |
|---|---|
| PASS | 確認驗收條件均有結果，整理交付與驗證狀態後完成 |
| RETRYABLE | 將明確修正指示交 Generator；達 3 次仍未通過則升級 |
| BACKTRACK | 問題來自需求或規格時，附差異與證據退回 Planner；達 2 次仍不清楚則升級 |
| ESCALATE | 存在人工裁決、外部依賴（使用者帳號、下載、Play 之後的畫面與聲音確認）、MCP 連不上或無法自動安全處理的阻塞時，停止相關工作並在對話裡問使用者 |

重試或回退時必須附上錯誤摘要、證據、已嘗試次數與下一步指示。不得無限重試，也不得以改寫驗收條件來假裝通過。

## 共通開發紀律

1. **先釐清，再動手**：明示假設與不確定性；重大歧義先詢問。
2. **簡單優先**：以最少且足夠的變更解決問題，不擴充未要求的功能。
3. **精準修改**：只改與需求直接相關的內容；不順手重構或格式化周邊程式。
4. **先讀再寫**：閱讀目標檔案、直接呼叫方、共用工具及資料／資產引用。
5. **定義可驗證目標**：每個重要需求要有對應的 `read_console` 驗證（或型別檢查）與明確的 Unity 人工檢查步驟。
6. **維持一致性**：遵循現有命名、架構、API、序列化及錯誤處理模式。
7. **評估變更影響**：共用模組、資料格式（CSV 欄位、Deck 資產、錄音檔）或 Builder 接線的修改，列出相依方與相容性風險。
8. **如實回報**：明確列出已驗證、未驗證、失敗及被阻塞的項目。
9. **保護既有工作**：工作區有其他未提交變更時，不還原、不覆蓋、不納入無關修改。

## 驗收回報格式

每次交付的結尾都用這個格式（可以精簡，但 `status`、`checked`、`uncertainties` 不可省）：

```text
status: PASS | FAIL | BLOCKED
scope: 本次處理範圍
checked:
  - criterion: 驗收條件
    result: PASS | FAIL | NOT_RUN
    evidence: 測試、命令輸出、檔案或人工檢查依據
issues:
  - type: RETRYABLE | BACKTRACK | ESCALATE
    summary: 問題摘要
    instruction: 可執行的下一步
    retry_count: 已嘗試次數
    max: 設定上限
uncertainties:
  - 尚未確認或未能驗證的事項
next_for_user:
  - 使用者要在 Unity 裡做的步驟（跑哪個選單、看哪一頁、應該看到什麼）
```

只有所有必要條件通過，或剩餘缺口已明確記錄並取得適當裁決，才可宣告完成。
